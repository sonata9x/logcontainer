## 수정 범위

1. Roll20 사용자 CSS: 블록용 서비스 래퍼가 absolute 위치의 기준점을 본문 아래로 밀고 있었다. full-width content-flow를 기준점으로 사용하고 block 래퍼는 static으로 변경했다. 원본 top/bottom/padding/CSS 문자열은 수정하지 않는다. 명시적 br도 세로 레이아웃으로 보존한다. 일반 대화, 색상, 이미지 크기, 수평 중앙정렬 규칙은 유지한다.
2. 사이드바: 시작 임계값 4→8px, 폴더 내부 영역 20~80%→30~70%, 일반 행 중앙에 삽입 판단 완충 영역을 추가했다. 자동 스크롤 속도/빈도를 제한했다. 실시간 재배치로 드래그 중인 행이 커서 아래에 나타나도 마지막 삽입 의도를 취소하지 않는다. 공유 폴더 이동 선택과 개인 배치/공동 hierarchy 모델은 변경하지 않는다.
3. 핸드아웃: 제목 18px, 제목/본문과 본문/이미지 간격 28px, 본문 줄간격 1.85.
4. 핸드아웃 팝업: 보기 헤더에 수정/삭제/닫기 아이콘을 한 줄로 배치했다. 닫기의 absolute 배치를 제거하고 접근성 이름과 툴팁을 제공한다. 게시 화면은 닫기만 표시한다.
5. 빈 페이지: 최초 내용 블록 등록 UI를 추가하고 기존 수동 블록 생성 API를 재사용한다. 페이지 꾸미기/세션 카드 저장은 pages 직접 UPDATE 대신 허용된 다섯 필드만 변경하는 권한 검증 RPC를 사용한다. 삭제/교체 시 DB 변경 성공 후에만 기존 카드 파일을 제거한다.
6. YouTube BGM: INSERT RETURNING에서 새 행의 owner를 직접 검사하도록 SELECT 정책을 보강했다. stable 함수의 테이블 조회에만 의존하지 않는다. 비동기 이후 사라지는 event.currentTarget 대신 form을 보관하고 오류/성공 모두 pending을 해제한다.
7. MP3 준비: 동일한 BGM SELECT 정책을 적용한다. 두 업로드 UI에서 25MB 이하 MP3를 사전 검사한다. GPT 사이드탭의 `prompt()` 미지원도 발견하여 MP3 제목 입력을 공통 페이지 내 dialog로 교체했다. 실패 안내도 dialog 안에 표시하며 재시도할 수 있다.

## 남은 검증 및 발견 사항

MP3 실제 업로드는 사용자 제공 파일로 승인받아 완료했다. 세션 카드 실제 업로드는 별도 승인을 받지 않아 수행하지 않았다. 권한 없는 사용자 및 공유 editor 계정의 DB 통합 테스트도 미완료다. 로컬 Supabase 환경변수가 없으므로 정적 회귀 테스트를 DB 통합 테스트로 간주하지 않는다.

GPT 사이드탭에서 기존 폴더 이름 변경의 `prompt()` 역시 지원되지 않는 오류를 발견했다. 이번 추가 수정은 MP3 업로드 입력창만 대상으로 하며, 폴더 이름 변경 및 기타 기본 prompt 기반 기능은 별도 개선 대상이다.

추가 요청: 대기 BGM은 페이지마다 한 곡만 허용하며 다른 곡 선택 시 교체한다. `202609170002_single_waiting_bgm.sql`은 기존 연결 중 가장 최근 곡을 남기고 unique partial index를 추가한다. 페이지 잠금·편집권한·곡 접근권한·업로드 확정을 검증하는 RPC 안에서 기존 연결 삭제와 새 연결 삽입을 원자적으로 실행한다. 실패 시 기존 연결을 복구하는 DB transaction이며, 본문 메시지 BGM과 보관함/음악 파일은 변경하지 않는다. 재생 아이콘은 원형 테두리를 제거하고 투명 배경/hover 및 기존 focus outline을 유지한다.

사용자가 `202609170002` SQL 적용을 완료했다. 실제 미리보기에서 기존 복수 대기 BGM이 최신 MP3 한 곡으로 정리됐으며, MP3→YouTube→MP3 교체 및 새로고침 후 한 곡 유지가 확인됐다. 재생 버튼 border 0px, 투명 배경도 확인했다. 음악 파일 및 보관함 항목은 유지했다.

추가 요청: 페이지 폰트는 글 제목/본문/개요에만 적용한다. `[data-font]`는 이제 log font 변수를 지정할 뿐 시스템 UI에 font-family를 직접 전파하지 않는다. 날짜·편집 버튼은 시스템 폰트를 사용하고 Rich Content의 명시적 font-family는 보존한다. 시스템 UI 폰트는 계정의 `user_preferences.system_font_family`에 저장한다. 기존 자신의 설정에 대한 SELECT/UPDATE RLS를 재사용하고, 허용된 7종만 API 및 DB constraint에서 검증한다. 설정 저장 즉시 sidebar/status/buttons/menus와 body portal에 적용하며 workspace 이탈 시 body 스타일을 복구한다. 기존 사용자는 Pretendard 기본값으로 시작한다. 게시 및 손님 화면의 콘텐츠 폰트도 제목/본문에만 적용하고 시스템 UI는 기본 서비스 폰트를 사용한다.

로컬 익명 브라우저 fixture에서 페이지 폰트=리디바탕, 시스템 폰트=고운 돋움으로 측정했다. 제목/개요/본문은 Ridibatang, 상태/날짜/편집 저장/팝업 메뉴·버튼은 GowoonDodum으로 분리됐다. 원본 사용자 CSS의 monospace 지정도 그대로 유지됐다. 이는 CSS 렌더링 검증이며 계정 설정의 실제 DB 저장 검증을 대신하지 않는다.

`202609170003_system_font_preferences.sql` 적용 후 계정 설정 저장 및 두 폰트 분리를 실제 미리보기에서 검증하고 main 병합·push한다. 핸드아웃의 모든 모바일 화면 크기 및 원본 전체 visual parity를 완료했다고 주장하지 않는다.

## 후속 수정: 핸드아웃 폰트 / 메시지 BGM

- 핸드아웃 보기의 실제 제목·내용과 편집 입력에 페이지 본문 폰트를 적용한다. body portal에 `data-font`를 직접 전달하며 편집/게시 화면 모두 페이지 폰트 변경을 따른다. 핸드아웃 버튼, 수정/삭제/닫기, 편집창 안내 제목은 시스템 폰트를 유지한다.
- 실제 미리보기에서 테스트 메시지에 기존 MP3를 연결했다. 재생 버튼 DOM은 있었지만 부모 `content-visibility:auto`의 paint containment 때문에 바깥으로 나온 아이콘이 잘렸고, 버튼 중심 hit test는 드래그 손잡이를 반환했다. 최적화 적용 대상을 wrapper가 아닌 실제 메시지 본문으로 한정하고 손잡이와 BGM의 가로 영역을 분리했다.
- 좁은 화면은 바깥 gutter가 없으므로 BGM 재생/보관 버튼을 메시지 위의 별도 34px 조작 행으로 배치한다. 사용자 Content CSS의 여백·위치 수치는 변경하지 않는다.
- BGM은 계속 `entry_id`에 연결하고 entry의 안정적인 React key를 유지한다. 화면 순서/index에 연결하지 않으므로 메시지를 옮겨도 같은 메시지에 귀속된다.
- BGM 수정 dialog는 현재 곡 제목과 재생 버튼을 표시하고 현재 선택 항목에 pressed 상태를 표시한다. 저장/해제 실패는 dialog 내부 안내로 표시하고 finally에서 pending을 해제한다. 이번 변경에는 추가 DB migration이 없다.
- 위 CSS/귀속/선택/폰트 경계를 확인하는 회귀 테스트 4개를 추가했다. 자동 테스트 통과만으로 실제 배포 후 이동·폰트·재생 검증을 대체하지 않는다.
- 로컬 CSS fixture의 일반 화면 및 390×844 화면에서 버튼 중심 hit test가 재생 버튼을 반환하고 손잡이 겹침 면적은 0이었다. 핸드아웃 제목·본문·두 입력은 Ridibatang, 닫기 버튼은 서비스 시스템 폰트였다. wrapper는 flow-root로 기존 margin containment를 유지하지만 바깥 컨트롤의 paint는 자르지 않는다.
- `440eb56` Vercel 미리보기에서 실제 테스트 메시지에 연결된 MP3 버튼의 클릭 영역을 확인했다. 수정창은 `현재 BGM / 시간이 데려온 운명`을 표시했다. 첫 메시지를 두 번째 메시지 아래로 드래그하고 새로고침 후 동일 entry id에만 버튼이 남는 것을 확인했다. 이동된 메시지 버튼으로 실제 재생했으며 paused=false, readyState=4, error=null, currentTime=9.75초였다. 확인 후 재생은 종료했다.
